# Tolaria 借鉴：学习工作区五阶段实施设计

## 一、目标与边界

本设计把 Tolaria 的五项产品思想适配到“标注星图”：学习收集箱、类型与关系视图、事实数据唯一且可重建、AI 读写边界、教学资产版本历史。

目标不是把标注星图改造成 Markdown 桌面知识库，也不迁移到 Tauri 或把 Git 暴露给学生。现有 FastAPI + Next.js、JSONL 学习记录、任务库、能力图谱和 chat 教学主链保持不变。新能力只服务数据标注学习过程。

## 二、总原则

1. `records.jsonl`、`decisions.jsonl`、`brief.json` 是学习事实；任何派生内容都能由它们重新生成。
2. 每个学生只能查看和修改自己的学习工作区；AI 不得跨用户读取或写入。
3. 快速记录优先于完美分类：学生的问题先被接住，再由 Coach 或教师整理。
4. 类型和关系用于更清楚地浏览学习状态，不替代既有评分、任务流和知识图谱。
5. 版本历史服务于教师、管理员和竞赛答辩，不向学生暴露 Git 操作细节。

## 三、总体实施顺序

```text
阶段 1：事实数据唯一 + 可重建
             ↓
阶段 2：AI 读写边界
             ↓
阶段 3：学习收集箱
             ↓
阶段 4：类型与关系视图
             ↓
阶段 5：教学资产版本历史
```

先完成前两项地基，再允许新增的收集箱数据写入；随后再做面向学生的收集和浏览功能。每个阶段独立设计、测试、提交，失败不阻塞其他已完成阶段。

## 阶段 1：学习事实数据唯一 + 可重建

### 目标

保证报告、提醒、知识图谱等展示内容始终来自可信学习记录。管理员能够修复派生数据，但不会误删学生记录、课程安排或进行中的任务。

### 数据分层

| 文件/数据 | 身份 | 普通修复 | 高级重建 |
|---|---|---:|---:|
| `records.jsonl` | 原始学习记录 | 只读 | 只读 |
| `decisions.jsonl` | 教学审计记录 | 只读 | 只读 |
| `brief.json` | 诊断事实 | 只读 | 只读 |
| `flow_state.json` | 进行中任务状态 | 保留 | 保留 |
| `knowledge_graph.json` | 派生知识图谱 | 重建 | 重建 |
| 报告、提醒摘要 | 运行时派生展示 | 刷新 | 刷新 |
| `course_plan.json` | 诊断派生课程 | 保留 | 根据诊断重建 |

### 功能设计

- 新增学习数据清单（manifest），记录事实数据版本、派生数据生成时间、最近一次重建的结果与错误摘要；它不复制学习记录。
- 管理员页提供“修复学习展示”：重建知识图谱并刷新报告/提醒摘要相关缓存或索引。
- 管理员页提供“重建课程计划”：展示影响说明并二次确认后，才依据 `brief.json` 更新 `course_plan.json`。
- 重建采用“先生成、后替换”策略：新数据生成和校验成功后才覆盖旧派生文件；失败时保留旧的可用文件。
- 每次操作输出结构化结果：处理项目、成功数、跳过原因、错误原因、生成时间。

### 权限与体验

- 只有教师/管理员能看到和调用重建操作；学生个人中心不展示此按钮。
- 数据为空时返回诚实的“暂无足够记录”结果，而不是报错或编造统计。

### 测试与验收

- 原始学习记录、审计记录、诊断文件和流程状态在任何重建后字节不变。
- 图谱可从固定样本记录稳定重建。
- 课程高级重建必须要求确认参数。
- 重建失败后旧图谱与旧课程仍可读取。

## 阶段 2：AI 读写边界

### 目标

把“AI 可以做什么”从提示词约束升级为服务层约束，确保新增工具不会让 AI 越权读取其他学生数据，或向不该写入的位置写内容。

### 设计

- 定义学习工作区资源类型：`learning_record`、`decision`、`inbox_item`、`course_asset`、`derived_view`。
- 每个资源操作经过统一的 scope 校验：当前用户身份、允许的资源类型、目标路径、读/写动作。
- 工具只接收业务参数，不接收任意文件路径；路径由服务层根据当前用户 scope 推导。
- 对 AI 写入实行最小权限：
  - Coach 可创建学习记录、追加待整理问题、写入决策。
  - Coach 不可改写历史评分记录，不可删除学生数据，不可修改任务库和规范库。
  - 管理员专用操作与普通聊天工具分离。
- 每次写入附加审计字段：来源工具、会话、时间、资源类型与操作结果；不记录无关的完整用户隐私内容。

### Tolaria 对应思想

借鉴其 MCP 工具的活动知识库检查、路径归属检查和“先读取 workspace 指令再操作”的模式；本项目继续使用现有多用户 ContextVar 与路径服务，不复制 Tolaria 代码。

### 测试与验收

- 模拟两个用户，A 无法读取、写入或枚举 B 的学习资源。
- 路径穿越、任意路径参数、未知资源类型全部被拒绝。
- Coach 写入合法收集箱项目会留下审计记录。
- 管理员重建接口不能通过普通聊天工具调用。

## 阶段 3：学习收集箱

### 目标

不让学生的疑问、标注台卡点或资料问题丢失，也不要求学生在提问时自己完成分类。学生可以先学习，后整理。

### 收集入口

- 聊天中明确的疑问、模糊但重要的学习需求。
- 标注台“这里有疑问”按钮及其当前任务、步骤、图片/视频/文本上下文。
- 上传或阅读资料时标记的疑问。
- 后续可接入报告或提醒上的“太笼统/我没懂”反馈；本阶段预留数据类型，不做反馈按钮。

### 数据模型

每条 `inbox_item` 只保存必要字段：

- `id`、`created_at`、`status`（`open` / `organized` / `archived`）。
- `source`（chat / annotation / material / feedback）。
- `raw_text`：学生原始问题。
- `context`：可选的任务 ID、知识点、教学步骤、资料引用。
- `suggested_type`：AI 的建议分类，可为空，不当作事实。
- `resolved_to`：整理后关联的知识点、错题、任务或课程计划项。
- `scope`、审计字段。

### 流程

1. 学生提出问题或点击疑问按钮。
2. 系统立即保存一条 `open` 项，并向学生确认“已记下，当前任务结束后一起处理”。
3. Coach 在合适的停顿点读取未整理项目，可解释、关联到知识点/任务，或保留待教师处理。
4. 整理完成后状态改为 `organized`，保留原问题和关联结果，绝不静默删除。

### 页面

- 个人中心增加“待整理问题”卡片：显示数量、最近一条和“继续处理”入口。
- 标注台保留现有“这里有疑问”入口，增加“已记录”反馈。
- 教师/管理员可查看各自权限范围内的待处理项目，不把所有学生数据混在同一列表。

### 测试与验收

- 各入口都能创建带正确上下文的项目。
- 记录疑问不会改变 `flow_state.json`，也不会阻断当前标注提交。
- 整理后可追溯到原始问题和关联对象。
- 同一学生的重复点击有去重窗口，避免一秒内生成多条相同项目。

## 阶段 4：类型与关系视图

### 目标

把已有的任务、知识点、错误模式、疑问和课程安排，变成学生与教师一眼可看懂的几类视图，而不是散落在多个 JSON 文件和图表里。

### 类型

- 待处理问题：来自收集箱且状态为 `open`。
- 已掌握知识点：有理论 `advance` 或实践 F1 达标证据。
- 确认易错点：有 `confirmed` 模式证据，单次错误不进入该视图。
- 待完成任务：课程计划和教学流共同决定的下一步任务。
- 学习资料：带版本的规范、任务说明、案例资料。

### 关系

- 问题 → 知识点。
- 问题 → 当前任务。
- 易错点 → 练习记录证据。
- 任务 → 前置知识点与课程模块。
- 报告 → 所依据的学习记录与教学资产版本。

关系只做导航与解释；评分依旧由 `annotation_check`，任务推进依旧由 `TeachingFlowEngine`，不新增第二套业务判断。

### 页面

在个人中心增加“学习工作区”页签或区块，默认展示四张卡片：待处理问题、已掌握知识点、确认易错点、下一任务。点击后进入相应筛选列表；空状态用引导文案解释如何产生第一条数据。

### 测试与验收

- 每个视图只显示当前用户数据。
- 单次 `unconfirmed` 错误不会进入“确认易错点”。
- 列表中的关联链接可回到来源任务、知识点或原问题。
- 数据缺失时显示空状态，不显示虚构统计。

## 阶段 5：教学资产版本历史

### 目标

让任务库、标注规范、评分规则和能力树的变更可追溯。教师、管理员和评委能够知道某个学习结果依据的是哪一版教学资产，但学生无需接触 Git。

### 版本范围

- `task_bank.json`：任务、答案、AI 预标注配置。
- `competency_tree.json`：能力树。
- 标注规范库及引用文档。
- 评分规则的可配置部分。

### 设计

- 为每一类教学资产生成内容摘要（版本号、内容哈希、生成时间、变更说明、来源提交）。
- 教师/管理员发布资产变更时填写简短说明，如“新增遮挡目标任务”“修正任务 3 的标签说明”。
- 新建学习记录、报告和评测结果时写入相关资产版本快照。
- 管理员页提供版本列表与差异摘要；只显示“新增/修改/删除了什么”，不开放学生操作 Git。
- 历史学习记录保留旧版本号，不会因任务库更新而被重新解释或改分。

### 测试与验收

- 相同资产内容重复计算得到相同版本哈希。
- 资产变更后新记录使用新版本，旧记录保持旧版本。
- 缺少 Git 信息时仍能使用内容哈希和本地时间工作。
- 版本历史不包含学生隐私内容或 API 密钥。

## 四、共同的错误处理与安全规则

- 所有新写入使用原子写入或“先写临时文件、校验后替换”。
- 任一派生操作失败，保留旧的成功版本并返回可理解错误。
- 管理员操作必须有权限校验、审计记录和用户可见的影响说明。
- 所有用户可见文案继续遵循现有可信表达规则：不编造数据、说明下一步、数据不足时明确说明。
- 不新增每轮聊天的大模型调用；分类建议可利用已有聊天回合，关键写入必须由服务层校验。

## 五、测试与交付策略

每个阶段至少包含：服务单元测试、用户隔离测试、对应 API 测试、前端 TypeScript 检查；涉及主流程页面时补 Playwright 冒烟测试。每阶段一个独立提交，不 push，直到用户确认一个完整大版本后再统一推送。

## 六、明确不做的内容

- 不迁移为 Tolaria/Tauri 桌面应用。
- 不直接复制 Tolaria 的 AGPL 代码。
- 不向学生开放 Git、文件路径、重建按钮或跨用户数据。
- 不重写既有评分、任务流、三层记忆、能力图谱和 cron 调度。
- 不把一次学习失误直接定性为长期薄弱点。
